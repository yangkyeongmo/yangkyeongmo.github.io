# MCP

Anthropic이 "Model Context Protocol"이라는 유명한 프로토콜을 공개한 지 두 달 뒤에, 나는 그것에 정말 열광했다. AWS Summit Seoul 2024에서 화려한 인프라 챗봇을 만든 회사들이 잔뜩 있었다. 드디어 그 간극을 한 번에 뛰어넘을 때가 됐다고 생각했다. 너무 신이 나서 동료들에게 MCP에 대해 배운 것을 공유하고, Cursor로 데모도 하고, 쓸모 있을 것 같은 MCP 서버 두 개까지 만들었다(오픈소스 했다[[1]](https://github.com/yangkyeongmo/mcp-server-apache-airflow)[[2]](https://github.com/yangkyeongmo/mcp-server-openmetadata)). MCP를 둘러싼 스포트라이트는 많이 가라앉은 듯하지만, MCP에 한정되지 않고 그것을 지나온 여정을 공유하고 싶었다.

MCP가 정말 멋져 보이는 이유는, 본질적으로 API이기 때문이다. MCP는 기존 시스템을 감싼 래퍼일 뿐이라고 프레임을 벗겨 말할 수도 있지만, 그게 아름다움이라고 말하고 싶다. LLM은 그냥 수학적 모델이다. 어떤 초기 상태가 주어지고, 질 좋은 데이터를 먹여 무언가 쓸모 있는 일을 하게 밀면, 그때 쓸모 있는 것이 된다. 하지만 여전히 모델일 뿐, 시스템 전체가 아니다. MCP는 모델과 우리가 이미 가진 계산 세계 사이의 간극을 잇는다.

이전에는 기존 시스템을 붙이는 일은 개발자만의 일이었다. 개발자들은 LangChain(요즘은 LangGraph)으로 복잡한 LLM 워크플로를 만들고 그 안에 호출을 심었다. 사람에게 추가 일이 생길 뿐 아니라, 일도 중복된다. 수백 명의 개발자가 사실상 같은 것을 반복해서 구현한다고 상상해 보라.

MCP는 공통 프로토콜이 없어서 생기던 중복을 줄인다. 어떤 개발자나 회사가 MCP 서버 구현을 보여 주면, 짜잔, 같은 것을 다시 개발할 필요가 없다. 다른 소프트웨어 엔지니어링 영역의 커넥터 패턴, 카프카의 Kafka Connectors 같다.

MCP 같은 것이 아예 없었던 것은 아니다. 예를 들어 ChatGPT Apps. 하지만 그 프레임워크를 쓰는 일은 한 플랫폼에 너무 묶여 있었다. 그런 식으로 접근들이 있었다. 하지만 MCP는 공개된 뒤로 엄청나게 퍼졌다. 내 추측은: 1. 오픈소스다 2. 이미 잘 발달한 모델을 활용하는 클라이언트-서버 모델이다 3. 극도로 일반적이다. 그리고 이유가 하나 더 있다.. 그냥 말이 된다.

Anthropic은 구현을 오픈소스 했다. 전통적으로 무언가를 공짜로 내놓는 것은 클로즈드소스에 비해 고유한 이점, 빠른 확산을 준다. 어차피 프로토콜이다. 표준이 되게 하려면 사람들이 써야 한다. HTTP처럼. HTTP에 RFC가 없었다고 상상해 보라. 누가 직접 구현해서 http 서버 프레임워크를 만들겠는가? 그래서 오픈소스는 좋은 생각이었다. 다른 선택이 없었을 것 같기도 하다.

MCP는 클라이언트-서버 모델을 쓴다. 이게 성공에 꽤 기여했을 것이라고 봤는데, 극도로 일반적이기 때문이다. 기존 시스템이 있다고? 서버로 감싸면 된다! 그렇게 쉽다. 이 모델은 IT 산업이 시작된 아주 처음부터 퍼져 있었다. MCP 클라이언트가 MCP 서버를 보는 방식은, 서버가 데이터베이스를 보는 방식과 같다. MCP 서버는 그 데이터에 대한 인터페이스이니, 사실상 LLM을 위한, 정확히는 MCP 클라이언트를 위한 데이터베이스다. 이게 MCP가 극도로 일반적인 이유도 설명한다. 서버와 데이터베이스가 얼마나 다양한지만 생각해 보라.

## Limitations

하지만 MCP를 쓰면 쓸수록, 아직 발전할 여지가 있다는 것을 알게 됐다. 1. 의도대로 동작하게 만들기 어렵다. 2. 서버를 구현하는 일이 생각보다 어려웠다. 3. 회사 보안 심사를 통과하기 어렵다.

MCP 클라이언트의 MCP 서버를 잔뜩 추가한다고 사용자 의도대로 빈틈없이 실행된다는 보장은 없다. MCP 서버는 도구, 리소스 등의 목록을 그 안에 박힌 설명과 함께 제공한다. MCP 서버가 등록되어 있으니 MCP 클라이언트는 어떤 도구를 쓸 수 있는지 안다. 하지만 다른 기술처럼 한계가 있다. 요즘 LLM에 익숙하다면 컨텍스트 한계에도 익숙할 것이다. 어떤 모델은 3M 토큰 윈도우에서도 일관된다고 주장하지만, 짧을수록 항상 낫다. LLM에게 도구를 쓰라고 어떻게 말하는지 궁금할 수 있다. 놀랍게도, 마법은 없다. MCP 클라이언트는 그냥 도구 목록을 LLM에 넘기고 고르게 한다. 내가 아는 한 다른 프레임워크의 함수 호출과 비슷한 방식이다. 이게 의미하는 바는, 너무 많은 도구가 붙으면 모델 성능을 해칠 수 있고, 모델이 사용자 의도에 맞는 도구를 고르지 못할 수도 있다는 것이다. MCP 클라이언트가 종종 제때 맞는 도구를 찾지 못하는 이유가 이것일 것이다.

[mcp-server-apache-airflow](https://github.com/yangkyeongmo/mcp-server-apache-airflow)와 [mcp-server-openmetadata](https://github.com/yangkyeongmo/mcp-server-openmetadata)라는 새 MCP 서버를 만들기 시작했을 때, 원클릭 개발 같은 게 아니었다. 에러가 많았고 문서가 제대로 되어 있지 않았다. 다른 MCP 서버를 쓸 때 `server/notification` 같은 숨은 메시지 타입이 있는 것을 알아챘고, 그걸 문서화한 레퍼런스로 찾아가기가 어려웠다.

MCP에 보안 프로토콜이 없다는 점(개발 중이라고 들었다) 외에, 에이전트에 MCP 서버를 붙이는 것 자체가 보안 위협이 된다. 회사에 구글 워크스페이스와 슬랙이 있다고 하자. 편하니까 각 서비스를 다루는 각 MCP 서버에 읽기·쓰기 권한을 줬다. 에이전트에게 말했다. "내 동료들에게 \<기밀 문서>를 알려 줘." 아주 과장된 예시지만, 프롬프트 엔지니어링을 아주 잘해서 에이전트가 "내 동료"가 누구고 어느 슬랙 채널에 사는지 이해했다 해도, 문제는 LLM이 확률적이라 무슨 일이 일어날지 확신할 수 없다는 것이다. 에이전트가 채널을 못 찾으면, 뭘 할까?

MCP 서버가 완전 자율 에이전트에 붙으면 더 나빠진다. 회사 비밀을 밖으로 공유하고 싶은 나쁜 마음인 직원이 아니어도, 보안 심사를 받지 않은 경로를 만들어서 말 그대로 회사의 모든 것을 가져갈 가능성이 있는 위험이 있다. 충분한 권한이 주어지면, "삭제"도 할 수 있다.

이에 대한 내 조언은, 예측 가능한 에이전트에만 MCP 서버를 붙이거나, 연동에 쓰는 API 토큰에 필요한 권한만 주라는 것이다. 에이전트가 읽기만 하고 쓰거나 삭제하지 못하면, 어떤 문제는 해결된다.

# Personal Lessons

MCP 자체 외에, ROI를 신경 쓰는 일의 중요성을 배웠다. 내가 만든 것 말고 다른 MCP 서버를 보면, 스타를 많이 받은 것을 볼 수 있다. 더 유명한 서비스일수록 스타가 더 많다. 그러니 ROI를 신경 써라. 진짜로. MCP 서버를 만드는 자원은, 나 같은 백엔드 엔지니어에게는 사실상 아무것도 아니었다. 관심을 다른 인기 서비스로 돌렸다면 스타를 더 받았을지도 모른다.

살기 정말 흥미로운 시대다. 나 같은 개발자들은 AI가 정말 우리 직업을 가져갈지 아직 두렵다. 하지만 엔지니어의 관점에서 이 기술의 성장은 매혹적이다. 눈이 거의 멀 지경이다. 이 마음가짐이 이 글, MCP가 무엇인지와 그 한계까지 쓰게 만들었다. 마천루 사이에 묶인 밧줄 위에 서서 건너려는 느낌도 들지만, 이런 시대를 사는 것은 다행이다.
